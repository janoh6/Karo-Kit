# Karo Kit v0.17.0 — Core Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace scattered `register_setting()`/`export_map()`/`export_labels()`/`uninstall.php` option declarations with one central registry, and replace class-string module registration with instantiable modules behind an adapter — with zero behaviour change to an existing install, except two incidental bug closures the user explicitly approved.

**Architecture:** New code lives in `src/`, namespaced `KaroKit\`, loaded by Composer PSR-4; existing code stays exactly where it is, loaded by a Composer classmap. `Option` is an immutable declaration; `Registry` is a flat collection deriving every cross-cutting view (uninstall list, export map, AJAX allowlist) from it; `Repository` gives typed reads. `Module` is an interface; `StaticModuleAdapter` wraps the existing `Karo_Kit_Gate`/`Karo_Kit_Etch` static classes unchanged, so this release ports the *foundation*, not the modules.

**Tech Stack:** PHP 8.4, WordPress 6.8, Composer (PSR-4 + classmap), PHPUnit 9.6 (harness already exists from v0.16.9).

**Spec:** `docs/superpowers/specs/2026-08-21-karo-kit-core-architecture-design.md` §2 (as amended — read the amendments at the top of §2.2 and §2.3 before starting; they correct three real gaps found while scoping this plan: a static `id()` that cannot survive `StaticModuleAdapter`, two missing interface methods the admin shell needs, and how `Registry` stays flat while `register_setting()` still needs per-module grouping).

## Deviations from the spec, made explicit before work starts

1. **`Option` gained `?Closure $defaultCallback`** (spec amendment, §2.2). `karo_kit_gate_registration_on`'s correct seed value is core's `users_can_register`, read around Gate's own filter on that same option — a static default cannot express this without silently reintroducing the bug v0.16.9 closed.
2. **v0.16.9's `Karo_Kit::maybe_seed_defaults()`, `SEED_VERSION`, `SEED_VERSION_OPTION` are deleted outright** in this release, superseded by the registry's generic seeding pass. Not left as dead code — there is never a question of which of two mechanisms governs a given option.
3. **`Module::id()` is an instance method**, not static as the spec's first draft had it (§2.3 amendment) — required for `StaticModuleAdapter` to return different ids per wrapped class.
4. **`Module` gained `renderPage()` and `optionGroup()`** (§2.3 amendment) — both exist on the current `Karo_Kit_Module` base class already; the admin shell needs them to keep working.
5. **Two pre-existing option-declaration bugs close as a side effect of correct registry declarations**, approved by the user: `karo_kit_accent_custom` was never in `uninstall.php`'s delete list (it now is); `karo_kit_etch_thumb_auto_limit` was missing from `export_map()` while its sibling `karo_kit_etch_thumb_threshold` was present (it now travels too). Both get one line in the v0.17.0 changelog.

## Global Constraints

- PHP floor `8.4`, WordPress floor `6.8` — unchanged, as declared in `karo-kit.php` headers.
- Indentation is **tabs** in every PHP file, matching the entire existing codebase.
- Yoda conditions (`'' === $x`) in new code, matching existing style.
- **No option is renamed.** Every `Option::$name` is the exact current string. This is checked explicitly in Task 14.
- **No behaviour change** except the two approved bug closures in Deviation 5. Every `register_setting()` call's `type`/`sanitize_callback`/`default` must be byte-for-byte equivalent to what it replaces — checked explicitly in Task 14.
- New PHP source lives under `src/`, namespaced `KaroKit\` mirroring its path (e.g. `src/Core/Options/Option.php` → `KaroKit\Core\Options\Option`).
- Existing classes under `includes/` and `modules/` are **not renamed, not moved, not namespaced** in this release — they are reached via a Composer classmap. The only changes to files under those two directories in this plan are: adding new static methods (`Karo_Kit_Gate::options()`, `Karo_Kit_Etch::options()`), removing now-redundant `register_setting()` calls and `export_map()`/`export_labels()` overrides, and deleting the superseded seeding method.
- Direct `$wpdb` calls (none are introduced by this plan) would need the existing `phpcs:ignore` convention; not applicable here.
- The test harness (`composer.json`, `phpunit.xml.dist`, `tests/bootstrap.php`, `.github/workflows/tests.yml`) already exists from v0.16.9 — this plan extends it, never recreates it. This machine has no local MySQL/MariaDB (established across every prior task in this project) — CI is the verification path for anything requiring a live WordPress+MySQL environment; verify by reading/hand-tracing locally and confirm for real via CI before tagging, exactly as v0.16.9 did.
- `.gitignore` already excludes `/vendor/`; `composer.lock` is already tracked (un-ignored in v0.16.9).

<?php
/**
 * A flat collection of every Option the kit declares, and every
 * cross-cutting view derived from it -- what used to be four separate,
 * hand-maintained lists (register_setting() calls, export_map(),
 * export_labels(), uninstall.php's array).
 *
 * Deliberately flat, not partitioned by module: uninstall, export and the
 * AJAX allowlist all need the merged set across every module, so nothing is
 * gained by Registry knowing which module an option came from. Where
 * register_setting() needs a per-module settings group, that scoping is a
 * caller-side loop (see Karo_Kit::boot()), not a Registry responsibility --
 * this is what wpType()/sanitizerFor() being public static is for.
 *
 * @package Karo_Kit
 */

namespace KaroKit\Core\Options;

if ( ! defined( 'ABSPATH' ) ) {
	exit;
}

final class Registry {

	/** @var array<string,Option> */
	private array $options = array();

	public function add( Option $option ): void {
		$this->options[ $option->name ] = $option;
	}

	public function get( string $name ): ?Option {
		return $this->options[ $name ] ?? null;
	}

	public function has( string $name ): bool {
		return isset( $this->options[ $name ] );
	}

	/** @return Option[] */
	public function all(): array {
		return array_values( $this->options );
	}

	/** @return string[] Names of options registered with WordPress and AJAX-writable. */
	public function settingNames(): array {
		return $this->namesWhere( static fn( Option $o ) => $o->setting );
	}

	/** @return string[] Names deleted on uninstall. */
	public function uninstallNames(): array {
		return $this->namesWhere( static fn( Option $o ) => $o->uninstall );
	}

	/** @return array<string,string> option name => 'value'|'page', for exported options. */
	public function exportMap(): array {
		$map = array();
		foreach ( $this->options as $option ) {
			if ( $option->export ) {
				$map[ $option->name ] = 'page' === $option->type ? 'page' : 'value';
			}
		}
		return $map;
	}

	/** @return array<string,string> option name => label, for exported options that have one. */
	public function exportLabels(): array {
		$labels = array();
		foreach ( $this->options as $option ) {
			if ( $option->export && null !== $option->label ) {
				$labels[ $option->name ] = $option->label;
			}
		}
		return $labels;
	}

	/**
	 * Seed every declared option with its default, once. add_option() is a
	 * genuine no-op when the row already exists, so a site's own deliberate
	 * choice is never overwritten -- this is safe to call on every
	 * admin_init as well as on activation.
	 */
	public function seedDefaults(): void {
		foreach ( $this->options as $option ) {
			$value = $option->defaultCallback ? ( $option->defaultCallback )() : $option->default;
			add_option( $option->name, $value, '', $option->autoload ? 'yes' : 'no' );
		}
	}

	/** @return string[] */
	private function namesWhere( callable $predicate ): array {
		$names = array();
		foreach ( $this->options as $option ) {
			if ( $predicate( $option ) ) {
				$names[] = $option->name;
			}
		}
		return $names;
	}

	/** WordPress's register_setting() 'type' string for one of our declared types. */
	public static function wpType( string $type ): string {
		return match ( $type ) {
			'bool'  => 'boolean',
			'int', 'page' => 'integer',
			'array' => 'array',
			default => 'string', // string, key, enum, hex
		};
	}

	/** The sanitize_callback for one Option, matching its declared $type exactly. */
	public static function sanitizerFor( Option $option ): callable {
		return match ( $option->type ) {
			'bool'  => static fn( $v ) => $v ? 1 : 0,
			'int'   => static function ( $v ) use ( $option ) {
				$n = absint( $v );
				if ( null !== $option->min ) {
					$n = max( $option->min, $n );
				}
				if ( null !== $option->max ) {
					$n = min( $option->max, $n );
				}
				return $n;
			},
			'page'  => 'absint',
			'key'   => 'sanitize_key',
			'enum'  => static function ( $v ) use ( $option ) {
				$v = (string) $v;
				return in_array( $v, $option->enum ?? array(), true ) ? $v : $option->default;
			},
			'hex'   => array( \Karo_Kit_Accent::class, 'normalise_hex' ),
			'array' => static fn( $v ) => $v,
			default => 'sanitize_text_field', // string
		};
	}
}
